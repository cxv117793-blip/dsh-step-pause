# 成本：N 越大越省的实测证据

一句话：**汇报间隔 N 每翻一倍，插件带来的总开销约减半。**
N=10 → N=20 实测省 **52.6%**，N=20 → N=40 省 **55.6%**，N=10 → N=30 省 **70.0%**。

下面的数字不是估算，是从本机 51 个真实会话、623 次自动注入、17,195 条模型调用里
逐条读出来的 token 计数（快照 2026-10-30）。复现命令在文末——你跑出来的样本会更大，
常数会在小数点后一位内浮动。

---

## 数据怎么来的

DSH 把每次模型调用的用量记在会话日志里：

```
<DSH_HOME>/sessions/<工作区>/<session-id>/session.v4.jsonl.zstd
```

两类事件是关键：

```jsonc
// 每次模型调用
{"type":"assistant/message","data":{"turn":3,"step":47,
  "usage":{"inputTokens":1240,"outputTokens":443,
           "cacheReadTokens":97111,"cacheWriteTokens":0}}}

// 插件注入的那条提示（不是模型写的）
{"type":"user/message","data":{"source":{"kind":"step-pause"},
  "content":[{"type":"text","text":"[自动 · 分步暂停 · 第 40 步…"}]}}
```

两个坑，脚本里都处理了：

1. **日志是多帧 zstd 拼接**，标准解压器只吃第一帧。要按帧魔数 `0x28b52ffd` 切开逐帧解。
2. **`user/message` 事件不带 `turn`/`step`**。要跟踪前面最近的 `step/start` 才能知道
   这条注入落在哪一步——否则统计会静默变成 0，而脚本不会报错，只会给你一张「处处省钱」的表。

## 三个测出来的常数

| 常数 | 含义 | 数值 | 分位 |
| --- | --- | --- | --- |
| **P** | 注入的提示词本身 | **265 token** | p25 181 / p75 351 |
| **R** | 模型为它写的汇报输出 | **430 token** | p25 339 / p75 629 |
| **B** | 一条已归档汇报，之后每一步还要多背的量 | **675 token** | 同轮 OLS，127 轮 |

**为什么 B 值得单独测。** 一条汇报写完之后并没有消失，它留在历史里直到会话结束，
之后每一步的 prompt 都要重新携带它一次。这个量决定了「N 调大到底省多少」，
而它既不能靠猜，也不能用「P+R 加起来」代替——那只是同量级，不是同一个量。

**两种独立方法互相印证：**

- **同轮 OLS**（主估计）：在每一轮内部，以「已归档汇报条数」为自变量、
  步序为控制变量做回归，得 B = **675**。
- **事件研究 + 对照组**：不能直接量「注入那一步 prompt 涨了多少」——上下文本来就在自然增长。
  必须设对照：同轮里相邻两步且中间没有注入的步作为 control。
  直接量注入当步得 **292**（≈P，因为汇报正文这一刻还没写出来）。
- **P + R = 695**，与 B = 675 同量级。

三条路指向同一个数量级，说明测的是真东西。**注意 292 和 675 不是矛盾**：
它们量的是两个不同时点——注入当刻多出的只是提示词本身；
汇报写完之后，它才变成长期要背的负担。混用这两个数会得出完全不同的成本结论。

## 缓存：注入不破坏前缀缓存

| 步骤类型 | cache 命中率 | 样本 |
| --- | --- | --- |
| 汇报步 | **99.1%** | 623 |
| 普通步 | **99.2%** | 15571 |

两者几乎无差别。原因是注入**追加在当前步消息批次的末尾**：

```js
messages: [...decision.messages, createNoticeMessage(...)]
```

前缀完全没变，所以前缀缓存照常命中，只有本步新增的那一小段按全价算。
**如果有人把注入插到历史中间，就会导致缓存全量重算——那是灾难性的。本插件没有这么做。**

（顺带回答一个常见误解：如果你觉得「每次总结都费一大笔」，那大概率是
**compaction 上下文压缩**在花钱，它按上下文长度触发，跟 N 无关。）

## 开销模型

设会话共 S 步，间隔 N，注入次数 k = ⌊(S−1)/N⌋。

```
一次性开销   = k × (P + R)                    ← 线性，∝ 1/N
连带重读     = Σ_{j=1..k} (S − jN) × B         ← 随步数二次放大，∝ 1/N
```

连带重读是主导项。直观理解：前几条汇报会被后面**几乎所有**剩余步骤携带，
最后一条只被携带几步。所以每次汇报的实际负担 ≈ B × 剩余步数。

**200 步会话的结果**（P=265, R=430, B=675）：

| N | 汇报次数 | 一次性开销 | 连带重读 | 合计 | 每步均摊 | 占会话总量 |
| --- | --- | --- | --- | --- | --- | --- |
| 1（每步都汇报） | 199 | 138,305 | 13,432,500 | **13,570,805** | 67,854 | 69.6% |
| 2 | 99 | 68,805 | 6,682,500 | **6,751,305** | 33,757 | 34.6% |
| 5 | 39 | 27,105 | 2,632,500 | **2,659,605** | 13,298 | 13.6% |
| 10 | 19 | 13,205 | 1,282,500 | **1,295,705** | 6,479 | 6.6% |
| 15 | 13 | 9,035 | 833,625 | **842,660** | 4,213 | 4.3% |
| **20（默认）** | 9 | 6,255 | 607,500 | **613,755** | 3,069 | 3.1% |
| 30 | 6 | 4,170 | 384,750 | **388,920** | 1,945 | 2.0% |
| 40 | 4 | 2,780 | 270,000 | **272,780** | 1,364 | 1.4% |
| 50 | 3 | 2,085 | 202,500 | **204,585** | 1,023 | 1.0% |
| 100 | 1 | 695 | 67,500 | **68,195** | 341 | 0.3% |

![开销随 N 变化](overhead-vs-n.svg)

- **N=10 → N=20：省 52.6%**
- **N=20 → N=40：省 55.6%**
- **N=10 → N=30：省 70.0%**

「占会话总量」按普通步 prompt 中位数 97,279 token × 200 步 ≈ 19,508,800 token 计算。
即使在最激进的 N=1，也只占到七成左右——但那是把引擎用来思考的预算拿去写流水账，
**这笔账不该这么算**：真正的代价是打断，不是 token。

## 换成分钱

`deepseek-flash` 单价（元 / 百万 token，2026-10 官方页快照，价格会变）：

| 项目 | 空闲时段 | 高峰时段 |
| --- | --- | --- |
| 输入 · 缓存未命中 | 1.00 | 2.00 |
| 输入 · 缓存命中 | 0.02 | 0.04 |
| 输出 | 4.00 | 8.00 |

> 高峰 = 北京时间周一至周五 9:00–12:00、14:00–18:00（法定节假日除外）；
> 其余时间与周末全天都是空闲价，**空闲价正好是高峰价的一半**。

N=20、200 步的一次会话（空闲价）：

```
一次性  9 条 × (265 输入未命中 + 430 输出)
        = 9 × (265×1 + 435×4)/1e6                    ≈ ¥0.0180
连带    624,600 token 中的 99.1% 走缓存命中
        命中部分 619,000 × 0.02/1e6                   ≈ ¥0.0124
        未命中部分 5,600 × 1.00/1e6                   ≈ ¥0.0056
                                              合计  ≈ ¥0.0360
```

注意那 0.9% 的未命中：它只占 token 量的零头，但因为未命中单价是命中价的 **50 倍**，
最后贡献了整笔的三成。所以「缓存命中率高」不等于「未命中可以忽略」。

## 什么时候该把 N 调大

省 token 只是副产品，真正的权衡是**发现延迟 vs 路径固化**：

| 场景 | 建议 N | 理由 |
| --- | --- | --- |
| 只是想看见进度 | 10 | 反馈及时，成本仍很低（6.8%，¥0.076／200 步） |
| 防目标漂移 | 15–20 | 汇报本身会固化「我当时在做什么」，越密路径依赖越强 |
| 探索型任务 | 8 | 容易走偏，需要频繁校准 |
| 已经很稳定 | 30+ | 几乎不花钱（¥0.023／200 步），只在关键节点对账 |

**但覆盖率是有上限的**：本机 257 个真实轮次里，每轮步数中位数只有 **28 步**。
按这个分布模拟，N=20 时只有 **59.5%** 的轮次会报上一次，N=30 掉到 **47.5%**——
超过一半的轮次完全静默。所以「调大」只能在**你确实都在跑长任务**时做；
如果你日常是一堆几十步的短轮次，把 N 调到 30 等于把插件关掉一半。
完整模拟表见 [README 的「默认值是怎么定的」](../README.md#默认值是怎么定的不是拍的)。

**注意**：N 调大省的是 token，不省「打断」。如果你在 N 大的时候仍然被汇报打断得难受，
该调的是提示词的写法，不是 N。

## 三个容易误解的点

1. **它不是额外发起一次请求。** 提示是追加进「本来就要发出去的那一批消息」，
   所以不增加请求次数。
2. **但它确实占掉那一步的输出预算。** 模型把这一步用来写汇报，
   而不是继续干活——所以「不多花一次调用」不等于「完全免费」。
3. **隐藏提示词不省钱。** `showPromptInChat: false` 只是让界面上看不见，
   提示词照样进模型上下文，token 照花。

## 自己复现

```bash
node tools/n-scaling-report.mjs                     # 你本机的数字
node tools/n-scaling-report.mjs --steps=500         # 按 500 步的会话估
node tools/n-scaling-report.mjs --n=10,20,40        # 只看这几档
node tools/n-scaling-report.mjs --markdown          # 生成上面那张表
node tools/n-scaling-report.mjs --svg --out=docs/overhead-vs-n.svg
```

脚本只读日志、不联网、不改任何文件。它扫的是**你自己的**
`~/.dsh/sessions/**/session.v4.jsonl.zstd`，所以换台机器跑会得到略有出入的数字——
那正是它该有的样子。样本量太小时（比如刚装几天）它会给出偏大的噪音，
建议至少积累几十次注入再看。

旧的单会话口径工具仍然保留：

```bash
node tools/cost-report.mjs "<session.v4.jsonl.zstd>"          # 空闲价
node tools/cost-report.mjs <路径> --peak --model=pro          # 高峰 + Pro
```

## 已知的测量局限

诚实写在这里，免得被数字唬住：

- **样本来自一台机器、一个模型、一种任务类型**（大量工具调用的编码任务）。
  换成别的任务，P/R/B 三个常数都会变，但 **N 翻倍→开销减半**这个关系由模型结构决定，不会变。
- **B 用的是中位数**，长会话尾部（上下文接近压缩阈值）的边际增长会更大。
- **没有量 compaction 的影响**。压缩会把最旧的区间换成摘要，如果一条汇报落在被压缩的区间里，
  它的连带成本会提前归零——本模型按「一直携带到最后」算，属于**保守估计**。
- **没有量「因间隔过长而多翻文件」的反向成本**。间隔太大时模型可能先查状态再多调几次工具，
  这部分没有计入。它会让 N 很大时的实际收益略低于本表。
